# AI-помощник TestRun — план MVP

> Статус: проектирование. Это не реализованная функция. Документ фиксирует безопасный объём первой версии и критерии приёмки.

## 1. Цель первой версии

Добавить в TestRun помощника, который по тексту требований или описанию функции предлагает черновик ручного тест-кейса. Пользователь проверяет и редактирует результат, и только после явного сохранения тест-кейс попадает в проект.

Первая версия решает одну задачу: **«Требование → черновик тест-кейса»**. Она не запускает тесты, не меняет существующие тест-кейсы и не анализирует скриншоты или историю прогонов.

## 2. Пользовательский сценарий

1. Пользователь входит в систему и открывает свой проект.
2. Нажимает «Создать тест-кейс с ИИ».
3. Вставляет текст требования. Это отдельное явное действие пользователя.
4. При необходимости указывает контекст: роль пользователя, платформу/браузер, ограничения и желаемый уровень детализации.
5. Нажимает «Сгенерировать».
6. TestRun показывает предварительный результат в редактируемых полях: название, предусловия, шаги, ожидаемые результаты.
7. Пользователь проверяет и редактирует каждый пункт.
8. Только по кнопке «Сохранить тест-кейс» результат записывается в проект. Отмена/закрытие страницы ничего не сохраняет.

Существующий сценарий ручного создания тест-кейса остаётся доступным и не меняет поведение.

## 3. Формат результата

Модель должна вернуть структурированный объект, а не произвольный HTML:

- `title` — краткое название;
- `preconditions` — массив предусловий;
- `steps` — массив объектов:
  - `action` — действие пользователя;
  - `expected_result` — проверяемый ожидаемый результат;
- `test_type` — positive / negative / boundary;
- `priority` — предложенная приоритетность;
- `assumptions` — предположения, которые сделал помощник;
- `open_questions` — вопросы, на которые исходного требования не хватило.

Каждый шаг должен быть конкретным и проверяемым. Неизвестные детали нельзя выдавать за факты: их нужно помещать в assumptions или open_questions. Нельзя придумывать реальные URL, учётные записи, пароли, тестовые данные или бизнес-правила.

Для одного требования MVP может предложить несколько сценариев (позитивный, негативный и граничный), но пользователь должен иметь возможность удалить лишние и сохранить только выбранные.

## 4. Архитектура

Предлагаемое разделение:

- `app/ai/` — отдельный модуль ИИ-функций;
- `provider.py` — интерфейс провайдера и адаптер конкретного API;
- `schemas.py` — схема и серверная валидация ответа;
- `prompts.py` — системные инструкции и версия промпта;
- `service.py` — orchestration: ограничения входа, вызов провайдера, разбор и проверка результата;
- отдельный blueprint/маршруты для страницы генерации и POST-запроса;
- отдельный шаблон предпросмотра и редактирования.

Существующий маршрут `create_test` не следует переписывать ради ИИ. После подтверждения данные должны сохраняться через общий внутренний сервис создания тест-кейса либо отдельный безопасный маршрут, который использует те же проверки, создание структурированных шагов и версионирование. Перед реализацией нужно проверить, можно ли вынести общую операцию сохранения без изменения старого поведения.

Провайдер должен быть заменяемым через адаптер. Конкретный поставщик и модель выбираются до подключения внешнего API; ключ хранится только в серверной переменной окружения, никогда в Git, HTML или браузерном JavaScript.

## 5. Приватность и безопасность

Обязательные правила MVP:

- Никакого фонового чтения проектов, тест-кейсов, прогонов, комментариев, скриншотов или наборов тестовых данных.
- Внешнему провайдеру передаётся только текст, который пользователь явно вставил в форму, и только после нажатия «Сгенерировать».
- Не отправлять пароли, секретные параметры, API-токены, персональные данные и содержимое секретных колонок. Перед отправкой выполнять проверку/предупреждение; пользователь должен иметь возможность отменить запрос.
- Не добавлять автоматически название проекта, существующие тесты или историю в запрос к модели.
- Входной текст считать недоверенными данными. Инструкции внутри требования не должны переопределять системные правила генератора.
- Ограничить размер запроса, число запросов на пользователя, время ожидания и максимальный размер ответа.
- Проверять типы, длины строк, количество предусловий и шагов на сервере. Не отображать сгенерированный HTML как доверенный.
- Не сохранять полный текст требований и ответ модели в технических логах. Для диагностики достаточно request ID, user ID, времени, статуса, провайдера/модели и агрегированных токенов/ошибок без содержимого.
- Предусмотреть выключатель ИИ через конфигурацию. Если ключ отсутствует или функция выключена, обычный TestRun должен работать как прежде.
- Ошибки провайдера, таймауты и некорректный JSON должны показываться понятным сообщением; никаких частичных записей в БД.

## 6. Данные и хранение

Для MVP не требуется новая таблица: черновик живёт в форме/сессии страницы и сохраняется только после подтверждения. Если позже понадобится история AI-генераций, это будет отдельное решение с настройкой срока хранения и приватности.

Сохранение подтверждённого тест-кейса должно создавать обычную версию №1 через существующую логику приложения. Генерация сама по себе не должна создавать TestCase, TestCaseVersion, TestRun или записи параметризации.

## 7. Стоимость и ограничения

- Лимит длины исходного требования.
- Лимит числа генераций на пользователя за период.
- Ограничение максимального ответа/числа сценариев.
- Таймаут внешнего запроса.
- Не выполнять автоматические повторные запросы, которые могут повторно тарифицироваться, без понятной политики.
- На первом этапе не обещать бесплатное или неограниченное использование: стоимость зависит от выбранного провайдера и модели.

Точные значения лимитов и провайдер фиксируются после выбора поставщика и оценки стоимости.

## 8. Этапы реализации

1. **Спецификация и выбор провайдера** — согласовать внешний API, обработку данных, модель и лимиты.
2. **Сервисный слой** — адаптер, схема ответа, валидация, безопасные ошибки и тесты без реальных платных API-вызовов (через mock).
3. **UI генерации** — форма ввода требования и контекста, явная кнопка отправки.
4. **Редактор результата** — проверка и изменение черновика до сохранения.
5. **Интеграция сохранения** — переиспользовать текущую логику создания тест-кейса и версий без регрессии старой формы.
6. **Тестирование** — права доступа, CSRF, лимиты, prompt injection, malformed output, таймауты, отключённый ИИ, отсутствие ключа, отсутствие сохранения без подтверждения, регрессия ручного создания.
7. **Ручная приёмка** — отдельная тестовая БД и тестовый ключ; production не затрагивать.

## 9. Критерии готовности MVP

- Пользователь может запросить генерацию только в собственном проекте.
- Без нажатия «Сгенерировать» никакие данные не уходят провайдеру.
- Без нажатия «Сохранить» тест-кейс не появляется в БД.
- Сгенерированный результат можно полностью отредактировать.
- Шаги имеют отдельные действия и ожидаемые результаты.
- Предположения и вопросы явно отделены от фактов.
- Секретные тестовые данные и токены не отправляются провайдеру.
- При выключенном ИИ все существующие функции приложения продолжают работать.
- Все проверки выполняются в CI; ручная приёмка проводится на изолированной копии.

## 10. Что не входит в MVP

- Автоматическое изменение существующих тест-кейсов.
- Автоматическое сохранение без подтверждения.
- Анализ результатов PASS/FAIL и скриншотов.
- Генерация кода Java/JUnit 5/Selenide.
- Автоматическое выполнение тестов.
- Обучение модели на данных пользователей.
- Массовая генерация сотен тест-кейсов за один запрос.

## 11. Решение, необходимое перед подключением API

Нужно выбрать провайдера. Архитектура остаётся независимой от поставщика, но первая реализация должна использовать один конкретный API. До выбора провайдера и проверки актуальных условий хранения/обработки данных внешний API не подключается.
