# Проектирование: параметры и наборы тестовых данных

**Статус:** проектное решение для MVP, реализация ещё не начата  
**Базовая версия:** `39629ce3933d95299d44c47184351090653677ae`  
**Ветка:** `feature/test-data-parameterization`

## 1. Цель

Дать возможность запускать один ручной тест-кейс с разными входными значениями, не копируя тест-кейс. Один запуск по строке набора данных создаёт отдельную запись `TestRun`. При запуске всего набора строки выполняются последовательно.

Существующие тест-кейсы без параметров должны продолжить работать без изменений.

## 2. Что уже есть в приложении и что переиспользуем

- `TestCase` — тест-кейс.
- `TestCaseVersion` — версия тест-кейса, к которой уже привязывается ручной или автоматический прогон.
- `TestStep` — структурированные шаги.
- `TestRun` — один результат выполнения.
- `StepRun` — снимок действия, ожидаемого результата, статуса и комментария на момент выполнения.
- `ApiToken` и `/api/run` — существующая авторизация API и приём результатов автотестов.

Важно: `StepRun.step_text` и `StepRun.expected_result` уже являются снимками. При параметризации в них нужно сохранять уже подставленный текст, а не шаблон с плейсхолдерами. Тогда история останется неизменной после редактирования тест-кейса или набора данных.

## 3. Область действия MVP

В первой версии набор данных принадлежит одному тест-кейсу. Общие наборы на уровне проекта, окружения и наследование переменных между тестами не входят в MVP.

Переменные разрешить в:
- предусловии;
- действии шага;
- ожидаемом результате шага.

Синтаксис: `{{login}}`, `{{password}}`, `{{expected_message}}`.

Подстановка выполняется серверной функцией по точному имени переменной. Нельзя использовать `eval`, Jinja-рендеринг пользовательского текста или выполнение кода. Неизвестные и незаполненные обязательные переменные должны блокировать запуск с понятной ошибкой.

Рекомендуемое ограничение имени: `[a-zA-Z][a-zA-Z0-9_]{0,49}`.

## 4. Предлагаемая модель данных

### TestDataSet
- `id`
- `test_case_id` — FK на TestCase
- `name`, `description`
- `created_by` — FK на User
- `is_active`
- `created_at`, `updated_at`

### TestDataColumn
- `id`
- `dataset_id` — FK на TestDataSet
- `key` — машинное имя переменной, уникальное в пределах набора
- `label` — подпись для интерфейса
- `data_type` — на MVP text / number / boolean
- `is_required`
- `is_secret`
- `position`

### TestDataRow
- `id`
- `dataset_id` — FK на TestDataSet
- `position`
- `values_json` — обычные значения
- `secret_values_encrypted` — зашифрованные секретные значения
- `is_active`
- `created_at`, `updated_at`

### Дополнения к TestRun
- nullable `data_set_id` и `data_row_id` для навигационной связи с исходными данными;
- `data_set_name_snapshot` и `data_row_snapshot` для отображения источника даже после деактивации набора;
- `data_values_snapshot` для обычных значений;
- `secret_values_snapshot_encrypted` для секретных значений;
- `precondition_snapshot` при необходимости исторического отображения подставленного предусловия.

Связи на набор и строку не должны каскадно удалять историю прогонов. Наборы и строки после использования деактивируются, а не удаляются физически. Исторический снимок в TestRun остаётся главным источником для воспроизведения данных.

Секретные поля нельзя хранить открытым текстом. Для них использовать отдельный ключ шифрования из переменной окружения `TEST_DATA_ENCRYPTION_KEY` (Fernet или эквивалентный проверенный механизм). Если ключ не настроен, сохранение секретных значений должно быть запрещено с понятной инструкцией. Не использовать Flask SECRET_KEY как долгосрочный ключ шифрования. Не выводить секреты в логи, HTML, PDF и сообщения об ошибках.

## 5. UX-поток

1. На странице тест-кейса появляется раздел «Тестовые данные».
2. Пользователь создаёт набор, добавляет колонки и строки.
3. В тексте шагов использует имена переменных, например `{{login}}`.
4. При нажатии «Запустить» выбирает:
   - обычный запуск без набора данных;
   - одну конкретную строку;
   - все активные строки набора последовательно.
5. Перед стартом система проверяет все плейсхолдеры и обязательные значения.
6. Каждая строка создаёт отдельный TestRun с тем же test_case/version и собственным снимком данных.
7. История показывает номер итерации, название набора, строку и статус. Старые прогоны не меняются после редактирования набора.

В MVP не нужно создавать отдельный долгоживущий объект «пакетный запуск»: достаточно последовательного сценария с серверной проверкой dataset и текущего индекса. Каждый сохранённый результат при этом остаётся самостоятельным TestRun. Нужно предусмотреть безопасное восстановление после обновления страницы и не допускать повторной записи одного и того же результата при двойном нажатии (idempotency token / run attempt token).

## 6. Подстановка и снимки

- Сначала получить утверждённую версию тест-кейса и строку данных.
- Проверить, что строка и набор принадлежат текущему тест-кейсу и текущему пользователю.
- Проверить обязательные поля, типы и все используемые переменные.
- Подставить значения в предусловие, действия и ожидаемые результаты.
- В StepRun сохранить resolved `step_text` и `expected_result`.
- В TestRun сохранить ID источника и снимок использованных значений.
- Секреты хранить только зашифрованными; в UI показывать маску и никогда не подставлять их обратно в обычные HTML-атрибуты или скрытые поля.

## 7. API для автотестов

Уже существующий `POST /api/run` принимает результаты автотестов. Его контракт нужно расширять только опциональными полями, чтобы старые клиенты продолжали работать.

Предлагаемый следующий контракт:
- endpoint чтения активных наборов и строк для конкретного test_case_id, защищённый существующим API-токеном;
- выдавать только наборы и строки, принадлежащие тест-кейсу пользователя-владельца токена;
- `POST /api/run` может принимать `data_set_id` и `data_row_id`; сервер сам проверяет принадлежность и сохраняет снимок строки. Не доверять произвольному snapshot, присланному клиентом;
- формат JSON стабилизировать и документировать до начала интеграции с Java/Selenide.

Для секретных значений предусмотреть отдельное явное разрешение токена или настройку доступа. По умолчанию API не должен возвращать секреты. Выдача секретов должна быть отдельной осознанной операцией и попадать в аудит без записи самих значений.

Пример будущего ответа (без секретных полей):

```json
{
  "test_case_id": 42,
  "dataset_id": 7,
  "dataset_name": "Авторизация",
  "rows": [
    {
      "row_id": 11,
      "values": {
        "login": "qa-user@example.test",
        "expected_message": "Успешный вход"
      }
    }
  ]
}
```

Это проектируемый контракт, а не существующий endpoint.

## 8. Миграции и обратная совместимость

- Использовать отдельную идемпотентную migration script по примеру существующего подхода проекта; не запускать `db.create_all()` на production как способ миграции.
- Все новые поля в TestRun nullable, чтобы старые строки БД оставались валидными.
- Не менять смысл существующих `TestRun` и `StepRun`.
- Старые API-клиенты с прежним JSON должны работать без изменений.
- Удаление тест-кейса должно корректно очищать новые наборы и строки; при этом нужно проверить, как сохраняется и удаляется история согласно текущей политике удаления тест-кейса.
- Не удалять файлы скриншотов и не менять механизм скриншотов в рамках этой функции.

## 9. План реализации

### Этап A — модель и CRUD наборов
- Модели и миграция.
- Создание, редактирование, деактивация наборов и строк.
- Управление колонками и проверка ключей.
- Проверки владельца проекта и CSRF.
- Тесты доступа между пользователями.

### Этап B — ручной запуск
- Плейсхолдеры и валидатор.
- Выбор одной строки / всех строк.
- Последовательный запуск с отдельным TestRun для каждой строки.
- Сохранение снимков и отображение в истории.
- Тесты на двойную отправку, обновление страницы, неизвестные переменные и редактирование набора после запуска.

### Этап C — безопасность секретов и отчёты
- Ключ шифрования и ротация/резервирование ключа.
- Маскирование в интерфейсе и PDF.
- Проверки отсутствия секретов в логах и ошибках.
- Документирование восстановления после потери ключа.

### Этап D — API для автотестов
- Чтение доступных наборов и строк.
- Расширение `/api/run` необязательными идентификаторами набора/строки.
- Контракт API и пример Java/JUnit 5/Selenide.
- Старый API smoke/regression test.

## 10. Обязательные тесты перед выпуском

1. Старый тест-кейс без параметров запускается как раньше.
2. Подстановка работает в предусловии, действии и ожидаемом результате.
3. Неизвестный плейсхолдер блокирует запуск до создания TestRun.
4. Обязательное пустое поле блокирует запуск.
5. Набор другого пользователя недоступен.
6. Строка другого тест-кейса не может использоваться.
7. Запуск всех строк создаёт отдельный TestRun на каждую активную строку.
8. У каждой итерации независимые статусы, комментарии и скриншоты.
9. История сохраняет исходные значения после редактирования/деактивации строки.
10. Секреты не попадают в HTML, логи, PDF и обычные API-ответы.
11. Старый контракт `POST /api/run` продолжает работать.
12. Миграция повторно запускается безопасно и не меняет существующие данные.
13. Удаление тест-кейса/проекта корректно обрабатывает новые связи и не оставляет осиротевшие файлы.

## 11. Что намеренно не входит в MVP

- Общие наборы данных на весь проект.
- Наследование переменных из окружений.
- Генерация случайных данных и функции faker.
- Комбинации всех значений нескольких таблиц (Cartesian product).
- Планирование параллельных итераций.
- Самостоятельный запуск автотестов из Test Runner.
- ИИ-генерация наборов данных.

Эти возможности можно обсуждать после выпуска и проверки базовой параметризации.
