# Параметризация тест-кейсов — техническая спецификация MVP

Статус: реализация MVP находится в feature/test-data-parameterization; PR #15 открыт и не объединён. Защита целостности при удалении и пакетных запусках вынесена в PR #16 и ещё требует синхронизации с этой веткой и общей регрессионной проверки.
Базовая версия проектирования: 39629ce3933d95299d44c47184351090653677ae.
Рабочая версия приложения и production-база этой документацией не изменяются.

## 1. Цель и границы MVP

Добавить к существующему тест-кейсу именованные переменные и табличные наборы данных. Один тест-кейс запускается с одной выбранной строкой или последовательно со всеми активными строками. Каждая итерация создаёт отдельный TestRun и сохраняется в истории.

Старые тест-кейсы без параметров продолжают работать без изменений. Существующий POST /api/run остаётся обратно совместимым.

В MVP входят:
- плейсхолдеры в предусловии, действии шага и ожидаемом результате;
- наборы данных, принадлежащие тест-кейсу;
- именованные колонки и строки;
- запуск одной строки или всех активных строк;
- отдельный TestRun на итерацию;
- неизменяемый исторический снимок использованных данных;
- безопасная обработка секретов;
- подготовка API для автотестов.

Не входят: глобальные переменные проекта, окружения, генерация данных, параллельные прогоны, AI и автоматическая генерация автотестов.

## 2. Уже существующая архитектура

В текущем коде есть:
- TestCase и TestCaseVersion — тест-кейс и история его версий;
- TestStep — структурированные шаги;
- TestRun — результат с автором, версией, источником manual/auto и длительностью;
- StepRun — исторические снимки текста шага, ожидаемого/фактического результата;
- API POST /api/run для приёма результатов автотестов с API-токеном.

Новая функциональность должна расширить эту модель. Не переписывать существующий механизм версий, снимков StepRun и API.

## 3. Пользовательский сценарий

1. В тест-кейсе пользователь открывает «Тестовые данные».
2. Создаёт набор, например «Авторизация».
3. Добавляет колонки login, password, expected_message и строки данных.
4. В предусловии, действиях или ожидаемых результатах использует плейсхолдеры {{login}}, {{password}}, {{expected_message}}.
5. Нажимает «Запустить тест» и выбирает одну строку либо все активные строки.
6. Для массового запуска приложение последовательно показывает форму каждой итерации.
7. История отображает каждую итерацию отдельно с названием набора/строки, статусом и временем.

Пользователь видит подставленные обычные значения. Секретные значения всегда маскируются.

## 4. Плейсхолдеры и подстановка

Синтаксис MVP: {{variable_name}}. Имя: [a-zA-Z_][a-zA-Z0-9_]*. Не поддерживать выражения, пробелы, точки, вложенные шаблоны или eval.

Подстановка применяется к:
- предусловию;
- действию шага;
- ожидаемому результату шага.

Правила:
- серверная подстановка только из выбранной строки;
- исходный текст TestCase/TestStep никогда не перезаписывается подстановкой;
- неизвестная переменная или пустое обязательное значение блокирует запуск до создания TestRun;
- значения — обычный текст, HTML экранируется штатными средствами Jinja;
- никаких eval, SQL, shell или интерпретации содержимого;
- старые кейсы без плейсхолдеров работают как прежде.

Проверять дублирующиеся ключи, формат имён, неизвестные плейсхолдеры и пропущенные значения.

## 5. Предлагаемая модель данных

Названия предварительные; сверить с текущими соглашениями и миграциями перед реализацией.

### TestDataSet
- id
- test_case_id — FK на TestCase
- name
- created_at, updated_at

### TestDataColumn
- id
- dataset_id — FK на TestDataSet
- key — имя переменной
- label — подпись для интерфейса
- is_secret — признак секрета
- position
- уникальность (dataset_id, key)

### TestDataRow
- id
- dataset_id — FK на TestDataSet
- name — например «Неверный пароль»
- values_json — обычные значения колонок
- is_enabled
- position
- created_at, updated_at

### Поля TestRun
- data_set_id nullable FK;
- data_row_id nullable FK;
- data_row_name_snapshot nullable;
- data_snapshot_json nullable — снимок обычных значений и маркеры секретов;
- data_snapshot_version — версия формата снимка.

Ссылка на строку нужна для навигации, но история должна отображаться из снимка. Строка/набор могут быть позже отредактированы или удалены.

## 6. Секретные значения

Не хранить пароль/секрет открытым текстом в values_json, снимке запуска, комментариях, PDF, логах или AI-контексте.

Рекомендуемый подход:
- обычные значения — в values_json;
- секретные — в зашифрованном виде в отдельном поле/структуре;
- шифрование только проверенной библиотекой, ключ — из переменной окружения, не из БД и не из Git;
- если ключ не настроен, сохранение секрета запрещено с понятным сообщением;
- в истории — только маркер [СЕКРЕТ СКРЫТ], без исходного значения;
- секрет не выводить в HTML, в том числе в скрытых data-атрибутах;
- секрет не включать в PDF, экспорт, AI-контекст и ошибки.

Реализация использует Fernet из библиотеки cryptography; ключ задаётся через TEST_DATA_ENCRYPTION_KEY отдельно от Flask SECRET_KEY. Если ключ отсутствует или некорректен, чтение/запись секретных значений завершается безопасной ошибкой без plaintext-fallback.

Эксплуатационные требования перед выпуском:
- сгенерировать отдельный случайный Fernet-ключ для каждого независимого окружения;
- хранить ключ только в защищённой конфигурации сервера/менеджере секретов, не в Git, БД, браузере или логах;
- включить ключ в защищённую резервную копию конфигурации с ограниченным доступом: потеря ключа сделает ранее сохранённые секреты нечитаемыми;
- не менять ключ без отдельной процедуры ротации и проверки возможности расшифровать старые значения;
- проверить маскирование секретов в истории, PDF, API-ответах и диагностических сообщениях на интеграционной базе.

## 7. Поведение запуска и истории

### Одна строка
- сервер проверяет владение проектом, тест-кейсом, набором и строкой;
- проверяет все плейсхолдеры и значения;
- строит контекст подстановки;
- форма показывает отрендеренные предусловие, действия и ожидаемые результаты;
- при сохранении TestRun и StepRun сохраняют подставленный текст;
- TestRun сохраняет ссылки на набор/строку и безопасный снимок данных.

### Все активные строки
В MVP — последовательный синхронный пользовательский сценарий без фоновой очереди:
- фиксируется список выбранных активных строк;
- каждая строка создаёт отдельный TestRun;
- после сохранения одной итерации открывается следующая;
- если пользователь прервал серию, сохранённые итерации остаются, несохранённые не создаются;
- итог показывает число завершённых итераций и PASS/FAIL/SKIP.

Защититься от двойной отправки/refresh одноразовым идентификатором итерации или другим механизмом идемпотентности.

### Историческая неизменность
- StepRun.step_text и StepRun.expected_result уже являются снимками; в параметризованном запуске туда записывается подставленный текст;
- TestRun.version_id продолжает фиксировать версию тест-кейса;
- снимок набора сохраняется в TestRun;
- редактирование/удаление набора не меняет старые результаты;
- PDF использует снимок и не раскрывает секреты.

## 8. API для автотестов — следующий подэтап

Существующий POST /api/run сохраняет прежний контракт.

Предварительный контракт чтения:
- GET /api/test-cases/<test_case_id>/data-sets
- GET /api/data-sets/<dataset_id>/rows

Маршруты уточнить после изучения стиля API. Возвращать обычные значения и метаданные секретных колонок; открытые секреты по умолчанию не отдавать.

Если автотестам понадобится получать секреты, это отдельное решение: отдельный scope токена, TLS, аудит, запрет логирования и возможность отзыва. В первом API-релизе лучше использовать тестовые несекретные данные или отдельный механизм секретов.

В существующий POST /api/run можно добавить необязательные поля data_set_id, data_row_id и идентификатор итерации/снимка. Старые клиенты без этих полей должны работать. Контракт зафиксировать тестами и документацией до выпуска.

## 9. Права доступа

- Все операции проверяют владельца проекта и тест-кейса через user_project или эквивалент.
- Нельзя получить/изменить набор по одному ID без проверки владельца.
- Нельзя привязать строку другого набора или другого тест-кейса.
- API проверяет токен и принадлежность тест-кейса пользователю.
- Не доверять скрытым полям HTML-формы; проверки делать на сервере.

## 10. Миграции и совместимость

- Сначала модели и тесты на изолированной БД.
- Новые поля в TestRun nullable, старые записи остаются валидными.
- Не пересоздавать существующие таблицы.
- Не менять текущий формат TestCase.steps и TestCase.expected_result в MVP.
- Миграция идемпотентная либо с явной версией схемы.
- Перед production-миграцией обязательны проверенная резервная копия и план отката.
- Не запускать production-миграцию в ходе разработки.

## 11. План реализации

1. Модели TestDataSet/TestDataColumn/TestDataRow, nullable-поля TestRun и миграция.
2. Сервис валидации/подстановки и unit-тесты.
3. CRUD интерфейс наборов и строк на странице тест-кейса.
4. Выбор строки и ручной запуск одной итерации.
5. Последовательный запуск активных строк.
6. История, статистика и PDF с итерациями и маскированием секретов.
7. API получения данных для автотестов; проверка обратной совместимости POST /api/run.
8. Интеграционные и регрессионные тесты на изолированной копии.

## 12. Обязательные тесты

- Старый тест без параметров работает как прежде.
- Подстановка в предусловии, действии и ожидаемом результате.
- Неизвестный плейсхолдер/отсутствующее значение блокирует запуск до создания TestRun.
- Некорректные/повторяющиеся ключи отклоняются.
- HTML/JS в значении выводится как текст и не исполняется.
- Данные другого пользователя/тест-кейса недоступны.
- Массовый запуск создаёт отдельный TestRun на каждую строку.
- Повторная отправка не создаёт дубль.
- Изменение/удаление набора не меняет историю.
- Секреты отсутствуют в открытом виде в БД, HTML, логах, PDF и API.
- Старый POST /api/run продолжает принимать прежний формат.
- Миграция сохраняет существующие TestRun, StepRun и версии.

## 13. Правило выпуска

Работа только в feature/test-data-parameterization, CI и изолированная тестовая копия с отдельной БД. Слияние и production deployment — только после проверки владельцем проекта. Не выполнять автоматическое слияние в production.
