## 2. Резервные копии

Пример для `/root/project_git`. Выберите защищённый каталог для копий вне репозитория и публичной директории.

```bash
cd /root/project_git
umask 077
BACKUP_DIR="/root/backups/testrunner-pre-pr7-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$BACKUP_DIR"
sqlite3 instance/test_runner.db ".backup '$BACKUP_DIR/test_runner.db'"
if [ -d instance/step-screenshots ]; then
  tar -czf "$BACKUP_DIR/step-screenshots.tar.gz" -C instance step-screenshots
else
  # No screenshots have been uploaded yet; still create a valid empty archive.
  tar -czf "$BACKUP_DIR/step-screenshots.tar.gz" --files-from /dev/null
fi
sqlite3 "$BACKUP_DIR/test_runner.db" "PRAGMA integrity_check;"
tar -tzf "$BACKUP_DIR/step-screenshots.tar.gz" >/dev/null
sha256sum "$BACKUP_DIR/test_runner.db" "$BACKUP_DIR/step-screenshots.tar.gz" > "$BACKUP_DIR/SHA256SUMS"
ls -lh "$BACKUP_DIR"
```

Ожидаемый результат `PRAGMA integrity_check` — `ok`. Если `sqlite3` отсутствует, резервная копия не создалась, проверка не `ok`, архив не читается или места мало — остановиться. Не удалять старые копии ради освобождения места. Ограничить доступ к резервным копиям уполномоченными администраторами.

## 3. Снять исходное состояние

- Открыть проект, тест-кейс, историю и существующий PDF, ничего не редактируя.

- Проверить, что текущий PDF открывается.
- Выполнить `systemctl is-active testrunner` и `journalctl -u testrunner -n 50 --no-pager`.
- Не публиковать журналы с персональными данными в открытом PR.

## 4. Ограниченный сценарий

Использовать временный тестовый проект/кейс с неважными данными. Если это невозможно, не редактировать реальные тест-кейсы — остановиться и согласовать другой способ.

1. Создать временный тест-кейс с двумя шагами.
2. Прикрепить разные тестовые PNG к обоим шагам и открыть оба изображения.
3. Переставить шаги местами и проверить, что скриншоты следуют за своими шагами.
4. Удалить один шаг и проверить, что вложение оставшегося шага не потерялось.
5. Выполнить прогон с тестовыми статусами и комментарием.
6. Изменить текст текущего тест-кейса и проверить, что история сохранила исходный текст, статус и комментарий.
7. Скачать PDF и проверить открытие, кириллицу, комментарий и изображение.
8. Проверить, что другой обычный пользователь не может открыть чужие проекты и изображения.
9. Удалить временный кейс штатным способом, если это безопасно.

При первой ошибке прекратить изменения и сохранить время, действие и безопасное сообщение об ошибке.

## 5. Критерии успеха

- Нет новых HTTP 500 и связанных с тестом ошибок в журнале.
- Скриншоты остаются с правильными шагами после перестановки.
- Удалённые вложения не показываются; оставшиеся не потеряны.
- Исторические шаги, статусы и комментарии не подменяются текущими значениями.
- PDF открывается, кириллица читаема, изображения видны.
- Проверка прав доступа не раскрывает чужие вложения.

## 6. Откат

Откат кода и восстановление данных — разные действия. Восстановление базы может удалить новые данные, созданные после копии.

1. При ошибке остановить тестовые действия и сохранить время, URL/действие, безопасный фрагмент журнала и текущий commit.
2. Если код на сервере не менялся, кодовый откат не нужен.
3. Если кодовое обновление было отдельно согласовано и применено, вернуть предыдущий подтверждённый commit по заранее согласованной процедуре и проверить службу.
4. Восстанавливать базу и вложения только при подтверждённой необходимости, после отдельного решения ответственного лица, с остановкой записи в приложение. Перед восстановлением сохранить ещё одну копию текущего состояния.
5. После отката проверить службу, вход, проект, историю, вложения и PDF.

Не запускать `git reset --hard`, не перезаписывать production DB и не перезапускать службу без согласованного плана и подтверждения ответственного.
