# Режимы подключения ИИ в TestRun

> Статус: проектное решение для следующего этапа после базового AI draft MVP. Документ не включает подключение реального платного API, не включает миграции и не разрешает включать ИИ на production.

## 1. Цель

Поддержать два независимых способа доступа к российскому AI-провайдеру:

1. **Облачный режим TestRun** — TestRun использует свой аккаунт провайдера. Режим можно включать только при подтверждённом бесплатном лимите либо после отдельного решения владельца о расходах. Если бесплатный лимит исчерпан, генерация останавливается; автоматический переход на платную оплату запрещён.
2. **Собственный ключ клиента (BYOK)** — клиент подключает собственный аккаунт и API-ключ провайдера. Стоимость запросов списывает провайдер с облачного аккаунта клиента по его тарифам. TestRun не принимает оплату и не выставляет счёт за токены.

Наличие одного режима не должно автоматически включать другой.

## 2. Обязательное согласие и уведомления

### До сохранения собственного ключа

Показать отдельное понятное предупреждение:

> Вы подключаете собственный аккаунт AI-провайдера. Запросы к ИИ могут быть платными и будут тарифицироваться непосредственно провайдером на вашем аккаунте. TestRun не контролирует тарифы и списания провайдера. Подключение ключа само по себе не запускает генерацию.

Сохранение ключа возможно только после явного подтверждения согласия.

### Перед генерацией через BYOK

Каждый запрос должен иметь явное действие пользователя. Перед отправкой показать предупреждение/подтверждение:

> Этот запрос будет отправлен выбранному AI-провайдеру и может повлечь списание средств с вашего аккаунта. Продолжить?

Пока подтверждение не получено, никакой сетевой запрос не выполняется. Нельзя считать сохранение ключа согласием на будущие платные запросы.

Если точную стоимость заранее определить нельзя, не показывать выдуманную сумму. Можно показать фактическое число токенов и расчётную стоимость после ответа, только если провайдер вернул usage и у нас есть актуальный тариф для конкретной модели. Такая оценка не заменяет биллинг провайдера.

### Для облачного режима TestRun

До первого запроса сообщить, что используется ресурс аккаунта TestRun. Не обещать «бесплатно» без подтверждённого тарифа/квоты. При отсутствии квоты или превышении лимита — понятное сообщение и остановка. Никакого автоматического платного fallback.

## 3. Безопасность API-ключей

- Не передавать ключ в HTML, JavaScript, URL, query string, cookie или браузерное хранилище.
- Не хранить ключ открытым текстом в базе данных.
- Шифровать ключ на сервере отдельным ключом шифрования из секретной конфигурации окружения; не использовать в качестве ключа шифрования обычный Flask SECRET_KEY.
- Если отдельный ключ шифрования не настроен, BYOK-функция остаётся недоступной; не использовать небезопасный fallback.
- Никогда не включать ключ, Authorization header, тело запроса или ответ провайдера в логи и сообщения об ошибках.
- Разделять ключи по пользователю/tenant. Пользователь может получить, заменить или удалить только собственную конфигурацию.
- После сохранения показывать только маску/последние символы ключа, никогда не возвращать исходное значение.
- При удалении ключа удалять зашифрованное значение. Учесть резервные копии базы и срок их хранения.
- Предусмотреть ротацию ключа шифрования и документированную процедуру восстановления. При невозможности расшифровать ключ — отключить BYOK и запросить повторное подключение, не пытаться отправлять повреждённое значение.
- Не отправлять ключ провайдеру в запросах к другим провайдерам; не использовать один ключ в чужом tenant.

## 4. Границы данных

Внешнему провайдеру передавать только требование, явно введённое пользователем для этой генерации, и минимальные системные инструкции/схему. Не передавать автоматически:

- название проекта и его описание;
- существующие тест-кейсы, историю и результаты прогонов;
- скриншоты и вложения;
- наборы тестовых данных, секреты, пароли, токены;
- профиль пользователя, email и идентификаторы tenant.

Перед текстовым полем показывать напоминание не вставлять реальные пароли, токены и персональные данные. В серверных логах не сохранять исходное требование, prompt, ключ, полный ответ или заголовки авторизации.

## 5. Настройки пользователя

В разделе настроек ИИ предусмотреть:

- режим: «Ресурс TestRun» / «Мой API-ключ»;
- поддерживаемого провайдера и модель;
- поле ввода ключа (только при добавлении/замене);
- обязательный folder/project ID провайдера, если это требуется API;
- статус подключения и маскированный идентификатор ключа;
- кнопки «Заменить ключ», «Удалить ключ», «Отключить ИИ»;
- краткую ссылку на тарифы провайдера и дату последней проверки тарифов.

Не выполнять платный пробный запрос при нажатии «Проверить подключение» без отдельного предупреждения. Для MVP можно отказаться от автоматической проверки ключа и сообщать о проблеме при первом подтверждённом запросе.

## 6. Стоимость и лимиты

- У BYOK нет расходов TestRun на токены клиента, но остаются расходы на инфраструктуру и поддержку, которые оцениваются отдельно.
- Для облачного режима TestRun вести внутренний учёт запросов и usage, если провайдер его возвращает.
- Ограничить длину требования, максимальный ответ, число запросов и таймаут.
- Не делать автоматических повторов запроса после сетевой ошибки: неизвестно, успел ли провайдер принять и тарифицировать запрос.
- Не обещать точную стоимость до запроса, если неизвестны тариф, модель или фактический token usage.
- Не включать платный fallback, авто-пополнение, смену тарифа или автоматическое списание.
- Установить разумные лимиты по умолчанию; возможность менять их — отдельное административное решение.

## 7. Архитектура

- Сохранить общий интерфейс provider adapter: генерация принимает требование и настройки конкретного вызова, возвращает валидируемый draft.
- Разделить resolver режима/tenant, хранение credential, provider adapter и UI подтверждения оплаты.
- Вся работа с ключом выполняется на сервере.
- Применять единый schema validator к ответам всех провайдеров.
- Ошибка одного провайдера не должна переключать запрос на другой аккаунт или ключ автоматически.
- Новая функциональность должна быть выключена по умолчанию и не влиять на ручное создание тест-кейсов, тестовые прогоны, PDF, API и историю.
- Перед добавлением таблиц/полей подготовить миграцию и тесты на отдельной тестовой БД. Не выполнять миграцию production в рамках разработки.

## 8. Этапы

1. Завершить проверку базового AI draft PR и его регрессии.
2. Зафиксировать provider-neutral интерфейс и конфигурацию без реального платного запроса.
3. Добавить UI описания режимов и уведомления/consent flow (с mock provider).
4. Добавить безопасное tenant-isolated хранение ключей только после проверки encryption design и миграции.
5. Добавить BYOK для одного выбранного провайдера, сначала только в тестовой среде.
6. Проверить отрицательные сценарии: нет ключа, ключ неверен, ключ удалён, чужой пользователь, нет согласия, превышены лимиты, timeout, provider error, повреждённый ciphertext, нет encryption key.
7. Добавить облачный режим TestRun только после подтверждения тарифов и доступной квоты; платный режим не включать без отдельного решения владельца.
8. Провести ручную приёмку на изолированной копии базы. Production не затрагивать.

## 9. Критерии приёмки

- Клиент видит предупреждение до сохранения BYOK ключа.
- Сохранение ключа не вызывает генерацию.
- Каждый платный запрос требует явного подтверждения.
- Без подтверждения запрос к провайдеру не отправляется.
- Списания по BYOK происходят на стороне аккаунта клиента; TestRun не списывает деньги.
- Ключ невозможно прочитать из браузера, URL, логов или чужого tenant.
- Ключ можно заменить, удалить и отключить.
- Ошибка/исчерпание лимита облачного режима не вызывает платный fallback.
- Ни один режим не активируется без явного выбора/настройки.
- Все существующие функции TestRun работают при выключенном ИИ.
- Все проверки используют mock provider; реальные платные запросы не выполняются в CI.
