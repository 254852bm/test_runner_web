# Безопасная проверка PR #9 на рабочем сервере

> Это инструкция, а не подтверждение готовности к выкладке. Не выполняйте её до одобрения PR #9, согласования окна низкой активности и ответственного за откат. Не отправляйте в чат секреты, пароли, токены или содержимое базы.

## 1. До начала

- Убедиться, что PR #9 `fix/project-screenshot-cleanup` одобрен ревьюером и все обязательные проверки завершились успешно.
- Сверить текущий production commit и целевой commit PR; записать их в журнал выкладки.
- Выбрать короткое окно низкой активности и предупредить пользователей.
- Проверить свободное место для копии базы, архива вложений и дополнительного запаса.
- Записать исходное состояние: `git status --short`, `git rev-parse HEAD`, `systemctl is-active testrunner`.
- Не выполнять `git pull`, `git reset`, `git checkout`, миграции или перезапуск службы до согласования и завершения предварительных проверок.

## 2. Резервные копии

Пример для `/root/project_git`. Используйте защищённый каталог вне репозитория и публичной директории.

```bash
cd /root/project_git
umask 077
BACKUP_DIR="/root/backups/testrunner-pre-pr9-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$BACKUP_DIR"
sqlite3 instance/test_runner.db ".backup '$BACKUP_DIR/test_runner.db'"

if [ -d instance/step-screenshots ]; then
  tar -czf "$BACKUP_DIR/step-screenshots.tar.gz" -C instance step-screenshots
else
  tar -czf "$BACKUP_DIR/step-screenshots.tar.gz" --files-from /dev/null
  echo "ВНИМАНИЕ: каталог instance/step-screenshots отсутствует; архив вложений пуст."
fi

sqlite3 "$BACKUP_DIR/test_runner.db" "PRAGMA integrity_check;"
tar -tzf "$BACKUP_DIR/step-screenshots.tar.gz" >/dev/null
sha256sum "$BACKUP_DIR/test_runner.db" "$BACKUP_DIR/step-screenshots.tar.gz" > "$BACKUP_DIR/SHA256SUMS"
sha256sum -c "$BACKUP_DIR/SHA256SUMS"
ls -lh "$BACKUP_DIR"
```

Ожидаемый результат `PRAGMA integrity_check` — `ok`; обе контрольные суммы должны пройти проверку. Если `sqlite3` отсутствует, копия не создана, проверка не `ok`, архив не читается или места мало — остановиться. Не удалять старые копии ради освобождения места.

**Важно о скриншотах:** пустой архив сам по себе не доказывает, что вложений нет. До выкладки подтвердите, где приложение хранит файлы, и проверьте все фактические каталоги хранения. Не считайте резервную копию вложений завершённой, пока этот пункт не подтверждён.

## 3. Зафиксировать исходное состояние

- Открыть существующий проект, тест-кейс, историю и PDF, ничего не редактируя.
- Записать число шагов и наличие скриншотов у выбранного тест-кейса.
- Проверить, что текущий PDF открывается.
- Выполнить `systemctl is-active testrunner` и `journalctl -u testrunner -n 50 --no-pager`.
- Не публиковать журналы с персональными данными в открытом PR.

## 4. Ограниченный smoke-тест

Использовать временный тестовый проект/кейс с неважными данными. Если это невозможно, не редактировать реальные тест-кейсы — остановиться и согласовать другой способ.

1. Создать временный тест-кейс с двумя шагами.
2. Прикрепить разные тестовые PNG к обоим шагам и открыть оба изображения.
3. Переставить шаги местами и проверить, что скриншоты следуют за своими шагами.
4. Удалить один шаг и проверить, что вложение оставшегося шага не потерялось.
5. Выполнить прогон с тестовыми статусами и комментарием.
6. Изменить текст текущего тест-кейса и проверить, что история сохранила исходные тексты шагов, статусы и комментарии.
7. Скачать PDF и проверить открытие, кириллицу, комментарии, версию/название исторического тест-кейса и изображения.
8. Проверить, что другой обычный пользователь не может открыть чужие проекты и изображения.
9. Удалить временный кейс штатным способом, если это безопасно.

При первой ошибке прекратить тестовые действия и сохранить время, действие и безопасное сообщение об ошибке.

## 5. Критерии успеха

- Нет новых HTTP 500 и связанных с тестом ошибок в журнале.
- Скриншоты остаются привязаны к правильным шагам после перестановки.
- Удалённые вложения не показываются; вложения других проектов не затронуты.
- Исторические шаги, статусы и комментарии не подменяются текущими значениями.
- PDF открывается, кириллица читаема, присутствуют историческая версия и комментарии.
- Проверка прав доступа не раскрывает чужие вложения.
- Проверена возможность отката кода и сохранности резервных копий; восстановление не выполняется без отдельного решения.

## 6. Откат

Откат кода и восстановление данных — разные действия. Восстановление базы может удалить новые данные, созданные после копии.

1. При ошибке остановить тестовые действия и записать время, URL/действие, безопасный фрагмент журнала и текущий commit.
2. Если код на сервере не менялся, кодовый откат не нужен.
3. Если кодовое обновление было отдельно согласовано и применено, вернуть предыдущий подтверждённый commit по заранее согласованной процедуре и проверить службу.
4. Восстанавливать базу и вложения только при подтверждённой необходимости, после отдельного решения ответственного лица, с остановкой записи в приложение. Перед восстановлением сохранить ещё одну копию текущего состояния.
5. После отката проверить службу, вход, проект, историю, вложения и PDF.

Не запускать `git reset --hard`, не перезаписывать production DB и не перезапускать службу без согласованного плана и подтверждения ответственного.
