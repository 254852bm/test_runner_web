# TestRun — описание проекта

> Документ подготовлен для технического руководителя, разработчика или ИИ-ассистента, которому нужно понять назначение, устройство и текущее состояние проекта. Он описывает репозиторий и функциональность, а не предоставляет доступ к production.

## 1. Краткое описание

**TestRun** — веб-приложение для управления ручным тестированием и интеграции с автоматизированными тестами. Основная сущность — проект, внутри которого хранятся тест-кейсы и результаты их прогонов.

Публичный адрес: https://testrun.pro  
GitHub: https://github.com/254852bm/test_runner_web

Проект развивается как самостоятельный продукт. Изменения ведутся в feature-ветках и pull request; production не должен обновляться до проверки изменений и отдельного согласования.

## 2. Для кого предназначен

- QA-инженеры, выполняющие ручные проверки;
- специалисты по автоматизации, отправляющие результаты автотестов;
- руководители тестирования, которым нужны история и отчётность;
- небольшие команды и учебные проекты.

## 3. Основные пользовательские сценарии

1. Пользователь регистрируется и входит в систему.
2. Создаёт проект и добавляет тест-кейсы.
3. Описывает предусловия, шаги и ожидаемые результаты.
4. Запускает ручной прогон, отмечает PASS / FAIL / SKIP, добавляет комментарии.
5. Просматривает историю прогонов и версии тест-кейса.
6. Формирует PDF-отчёт и анализирует Dashboard.
7. Создаёт обращения в поддержку.
8. При наличии API-токена подключает автоматизированные тесты и отправляет результаты.

## 4. Функциональные области

### Проекты и тест-кейсы
Проекты группируют тест-кейсы. Тест-кейс содержит название, предусловие и упорядоченные шаги с ожидаемыми результатами. История версий фиксирует изменения содержания теста.

### Ручные прогоны и история
Прогон хранит итоговый статус, длительность, комментарии и результаты отдельных шагов. История используется для анализа предыдущих запусков и формирования отчётов.

### Скриншоты и PDF
Скриншоты могут быть связаны с ожидаемыми результатами шагов и комментариями прогонов. Файлы хранятся отдельно от SQLite в каталоге instance приложения. PDF-отчёты формируются через ReportLab и поддерживают кириллицу.

### Dashboard и интерфейс
Dashboard показывает статистику результатов. Интерфейс использует Jinja2, Bootstrap, CSS и JavaScript; предусмотрены светлая и тёмная темы и боковая навигация.

### Личный кабинет, поддержка и администрирование
Личный кабинет показывает данные и статистику владельца. Поддержка реализована как обращения и переписка. Административные возможности доступны только уполномоченному администратору и включают управление пользователями и обработку обращений. Точные права определяются серверными проверками.

### Параметризация тест-кейсов — feature branch
В ветке `feature/test-data-parameterization` реализуется повторное использование одного тест-кейса с различными значениями переменных вида `{{login}}`. Модель включает наборы данных, колонки, строки, исторические снимки и batch для последовательного запуска. Есть API получения наборов/строк и отправки результатов автотестов.

Секретные колонки шифруются отдельным Fernet-ключом `TEST_DATA_ENCRYPTION_KEY`. API не выдаёт секреты по умолчанию: требуется и отдельное разрешение конкретного API-токена, и явный opt-in заголовок. Секреты не должны попадать в обычные JSON-снимки, историю, PDF или логи.

**Статус:** функция описана в feature-ветке и требует ручной приёмки на изолированной тестовой копии, включая проверку миграции SQLite, секретов, UI, API, истории и обратной совместимости.

### Защита целостности удаления — отдельный PR
PR #16 содержит исправления удаления связанных параметризованных данных, обработку batch при удалении строки и защиту от повторной отправки одной итерации. Эти изменения должны проверяться совместно с веткой параметризации до объединения.

## 5. Технологический стек

- Python;
- Flask;
- SQLAlchemy;
- SQLite в текущем развёртывании;
- Jinja2, HTML, Bootstrap, CSS, JavaScript;
- ReportLab для PDF;
- cryptography/Fernet для шифрования секретных тестовых значений;
- Gunicorn и Nginx на Ubuntu VPS.

Точные версии зависимостей следует брать из файлов зависимостей текущего коммита, а не из этого обзорного документа.

## 6. Структура репозитория (логические области)

- `app/` — Flask-приложение, маршруты, модели, API и сервисная логика;
- `templates/` — Jinja2-шаблоны интерфейса;
- `static/` — CSS, JavaScript и статические ресурсы;
- `tests/` — автоматические тесты;
- `scripts/` — обслуживающие и миграционные скрипты;
- `docs/` — пользовательская, API- и эксплуатационная документация;
- `instance/` — локальные/серверные данные экземпляра приложения; не должны попадать в Git.

## 7. Данные и безопасность

- Доступ к проектам и тестовым данным должен проверяться на сервере по владельцу.
- API-токены передаются в заголовках, не в URL.
- Секреты не следует хранить в обычных колонках, логах, комментариях или CI-артефактах.
- `SECRET_KEY` Flask и `TEST_DATA_ENCRYPTION_KEY` имеют разные назначения.
- Потеря Fernet-ключа делает существующие зашифрованные значения нечитаемыми; ключ и резервная копия базы должны храниться согласованно и защищённо.
- Миграции сначала выполняются на копии БД. Скрипт миграции должен получать явный путь к тестовой БД и не должен создавать отсутствующий файл БД.
- Нельзя коммитить `.env`, production SQLite, API-токены, скриншоты пользователей или содержимое `instance/`.

## 8. Разработка и выпуск изменений

1. Получить актуальный код и определить базовую ветку.
2. Изучить PR и связанные изменения, проверить совместимость.
3. Разрабатывать в отдельной feature/fix-ветке.
4. Запустить компиляцию, проверку шаблонов и полный набор тестов в CI.
5. Проверить ручные сценарии на изолированной тестовой копии и тестовой SQLite-БД.
6. Создать проверенную резервную копию тестовой БД; проверить `PRAGMA integrity_check`.
7. Только после приёмки подготовить отдельный план обновления production, backup и rollback.
8. Не объединять PR и не выполнять production deployment без явного решения владельца проекта.

## 9. Что важно проверить перед выпуском параметризации

- Миграция существующей SQLite-БД на тестовой копии;
- создание/редактирование/удаление наборов, колонок и строк;
- подстановка переменных в предусловия, шаги и ожидаемые результаты;
- одиночный и последовательный запуск, поведение при удалении строки;
- параллельные и повторные POST-запросы;
- сохранение исторических снимков;
- отсутствие секретов в обычных JSON-полях, логах, истории и PDF;
- API с разрешением и без разрешения на секретные данные;
- обратная совместимость старого `POST /api/run`;
- сохранность существующих скриншотов, отчётов и пользовательских данных.

## 10. Идеи дальнейшего развития

Ниже — идеи, а не обещание уже реализованной функциональности. Их нужно оценивать отдельно:

- AI-помощник, который превращает требования или пользовательское описание в черновик тест-кейса; пользователь всегда проверяет и подтверждает результат.
- Расширенные параметры и шаблоны данных для разных окружений.
- Более глубокая интеграция с CI/CD и автоматизированными фреймворками.
- Командная работа, роли и совместное владение проектами.
- Перевод SQLite на PostgreSQL при росте нагрузки и числа пользователей.

## 11. Правила для ИИ-ассистента, работающего с проектом

- Сначала изучить текущую ветку, статус Git и последние коммиты.
- Не считать описание в документации доказательством, что функция есть в текущей ветке: проверять код.
- Не менять production, production-БД, секреты и настройки сервиса.
- Не удалять и не перезаписывать `instance/`, SQLite-файлы, скриншоты и резервные копии.
- Не выполнять миграции на production без отдельного разрешения.
- Сохранять обратную совместимость существующего API и пользовательских сценариев.
- Делать небольшие изолированные изменения, добавлять регрессионные тесты и запускать полный CI.
- Не объединять PR и не выкладывать изменения без явного согласования владельца.
- Если требования неоднозначны, задать один конкретный вопрос, прежде чем менять поведение или данные.
