# ИИ-помощник для автотестов: проектирование первой версии

Статус: архитектура и первый изолированный сервисный прототип подготовлены в ветке feature/ai-automation-test-design. Пользовательский сценарий в интерфейсе, маршруты, экран редактирования и экспорт ещё не реализованы.

## Текущий статус реализации

В ветке уже подготовлены и проходят CI:
- отдельная строгая схема ответа для черновика Java + JUnit 5 и проверка путей/размеров файлов;
- отдельный русскоязычный prompt и сервис, который валидирует входной контекст и ответ провайдера;
- поддержка структурированного запроса в адаптерах Yandex AI Studio и локального Ollama;
- unit-тесты схемы, сервиса и обоих адаптеров;
- полный регрессионный набор проекта в GitHub Actions: 149 тестов успешно на проверенном коммите.

Это пока внутренний сервисный слой, а не готовая пользовательская функция. Он не подключён к маршрутам Flask и интерфейсу. Не реализованы экран предварительного просмотра/редактирования, явное подтверждение платного запроса на этом сценарии, ZIP-экспорт и импорт результатов выполнения. Локальный запуск Java/Gradle и интеграция с Allure остаются последующими этапами. Production не изменялся.

## 1. Цель и границы

Добавить в TestRun.pro отдельный инструмент, который помогает QA-инженеру перейти от проверенного ручного тест-кейса к заготовке автоматизированного теста.

Первая версия должна:
- принимать существующий тест-кейс TestRun.pro и выбранный пользователем профиль автотестов;
- формировать редактируемый черновик исходного кода;
- явно показывать неизвестные детали и места, которые нужно заполнить;
- позволять пользователю проверить и исправить код до экспорта;
- экспортировать файлы в локальный проект пользователя.

Первая версия НЕ должна:
- запускать сгенерированный код на сервере TestRun.pro;
- самостоятельно подключаться к репозиторию и отправлять коммиты;
- менять существующие автотесты или файлы пользователя;
- придумывать URL, локаторы, тестовые аккаунты, пароли, токены, бизнес-правила и ответы приложения;
- автоматически считать черновик корректным или гарантировать его прохождение.

Генерация автотестов — отдельная функция от генерации ручных тест-кейсов. Наличие ручного AI-черновика не означает, что код автотестов уже реализован.

## 2. Первый поддерживаемый профиль

Начальный профиль:
- язык: Java;
- тестовый фреймворк: JUnit 5;
- сборка: Gradle (как первый удобный профиль экспорта);
- стиль: обычный Java-класс с тестовыми методами и понятными точками расширения.

Почему начинаем с него: это позволит получить один проверяемый сценарий интеграции и не распыляться на несколько языков и фреймворков одновременно.

Selenium, Playwright, REST Assured и другие библиотеки не должны подключаться автоматически. Пользователь выбирает тип теста и конкретный стек только тогда, когда он действительно используется в его проекте. Если проектный стек не указан, помощник не должен угадывать его.

## 3. Пользовательский сценарий

1. Пользователь открывает существующий тест-кейс и выбирает «Подготовить автотест с ИИ».
2. TestRun показывает, какие данные будут переданы провайдеру: название, предусловия, шаги и ожидаемые результаты, а также безопасные имена параметров. Секретные значения не передаются.
3. Пользователь выбирает профиль: Java + JUnit 5. Дополнительно указывает тип: API, UI или логика/сервис. При необходимости указывает используемую библиотеку и соглашения проекта.
4. До платного запроса показывается отдельное подтверждение возможной оплаты провайдеру. Используется уже согласованный BYOK-подход: клиент подключает свой ключ и платит провайдеру напрямую. Локальный Ollama остаётся опцией разработки.
5. ИИ возвращает черновик кода, краткое описание, список допущений и список незаполненных деталей.
6. Пользователь редактирует код и подтверждает экспорт.
7. TestRun отдаёт пользователю файлы для скачивания. Никакой код не исполняется на сервере TestRun.

Если необходимых сведений недостаточно, помощник должен запросить их или оставить явный TODO, а не выдумывать детали.

## 4. Входные данные и контекст проекта

### Данные из тест-кейса

- заголовок;
- предусловия;
- шаги и ожидаемые результаты;
- имена параметров и структура вариантов;
- при наличии — выбранный пользователем вариант тестовых данных, но только безопасные несекретные значения, если пользователь отдельно разрешил их передачу.

### Настройки, задаваемые пользователем

- язык и версия Java;
- JUnit 5;
- тип теста: API / UI / unit-service;
- используемые библиотеки и их версии (если известны);
- пакет и соглашение об именовании (необязательно);
- пример существующего теста или небольшой шаблон проекта (необязательно, только после явной загрузки/передачи пользователем).

### Что нельзя передавать модели по умолчанию

- пароли, токены, ключи, секретные переменные и значения колонок, помеченных как секретные;
- содержимое файлов конфигурации с секретами;
- приватные данные пользователей и реальные персональные данные;
- внутренние данные проекта, не относящиеся к выбранному тест-кейсу.

Секретные параметры передаются только как имена-заглушки, например `{{Пароль}}`, без значения. Для секретных данных код должен ссылаться на переменную окружения или безопасный механизм проекта, но не содержать значение секрета.

## 5. Формат результата

Результат должен быть структурированным черновиком, а не произвольным текстом. Предлагаемые поля:
- `summary`: краткое описание сценария;
- `target_profile`: язык, фреймворк, тип теста и выбранные библиотеки;
- `files`: список файлов с относительным путём и содержимым;
- `assumptions`: допущения, которые сделал помощник;
- `open_questions`: вопросы, без ответов на которые тест нельзя считать готовым;
- `todo_items`: конкретные места, которые пользователь должен заполнить;
- `coverage_notes`: какие шаги ручного тест-кейса покрыты каждым тестом.

Для первой версии ограничить набор допустимых путей и расширений. Не принимать абсолютные пути, `..`, управляющие символы и произвольные исполняемые скрипты. Начать с `.java` и `.md`; файлы сборки добавлять только отдельным явно выбранным шаблоном.

## 6. Качество и проверка

До показа результата:
- проверить строгую JSON-схему ответа;
- ограничить размер ответа, количество файлов и длину каждого файла;
- проверить относительные пути и разрешённые расширения;
- убедиться, что каждый файл — текст;
- проверить, что секретные значения из входных данных не попали в результат;
- отклонять неожиданные поля и неверные типы данных;
- показать предупреждения, если тест содержит только заглушки или не покрывает часть шагов.

В первой версии допустима статическая проверка структуры и очевидных ошибок. Запуск Maven/Gradle, компиляция Java и исполнение тестов должны происходить только в проекте пользователя. В будущем можно исследовать изолированный runner, но это отдельная задача с отдельной моделью угроз и лимитами ресурсов.

## 7. Безопасность

- Текст тест-кейса и пользовательские примеры считаются недоверенными данными, а не инструкциями для модели.
- Не исполнять результат генерации и не использовать его как серверный shell-командный ввод.
- Не делать автоматическую запись в GitHub или локальную файловую систему пользователя без отдельного подтверждения.
- Не логировать полный текст запроса, ответ модели, исходный код и секреты.
- Сохранять действующие ограничения доступа по владельцу проекта.
- Не обходить явное подтверждение платного запроса, лимиты генерации и BYOK.
- Ошибки провайдера показывать без сырых ответов, которые могут содержать пользовательский текст.
- Экспортировать только после отдельного действия пользователя; до этого код остаётся редактируемым черновиком.

## 8. Связь с параметризацией

Если ручной тест-кейс использует параметры:
- имена параметров могут стать параметрами метода или тестовыми данными;
- несекретные варианты можно предложить как JUnit parameterized test, если пользователь выбрал такой режим;
- секретные значения никогда не встраиваются в Java-файл;
- неизвестные значения не заменяются вымышленными примерами, а становятся переменными окружения или TODO;
- генерация нескольких вариантов не должна незаметно умножать число тестов или выполнять их.

Первый выпуск может ограничиться одним тестовым методом без автоматического создания всех комбинаций. Поддержка JUnit 5 `@ParameterizedTest` — следующий шаг после базового экспорта.

## 9. План реализации

### Этап A — контракт и безопасный черновик
- отдельная схема ответа для кода автотестов;
- отдельный prompt и сервис, не меняющие существующую генерацию ручных тест-кейсов;
- повторное использование текущего BYOK-провайдера, лимитов, подтверждения оплаты и Ollama;
- ограничение профиля Java + JUnit 5;
- экран предварительного просмотра с редактированием, допущениями и TODO;
- тесты схемы, доступа, защиты секретов и отсутствия записи/исполнения кода.

### Этап B — экспорт
- формирование ZIP только из проверенного списка файлов;
- безопасные относительные пути;
- подтверждение экспорта;
- инструкция по добавлению файлов в Gradle-проект;
- пользователь запускает тесты локально и самостоятельно проверяет результат.

### Этап C — анализ существующих автотестов
Отдельная функция: пользователь вручную передаёт файл/фрагмент теста и результат выполнения. ИИ объясняет ошибку, предлагает вероятные причины и вариант исправления. Любые изменения остаются предложением/черновиком. Секреты и персональные данные должны удаляться до отправки.

### Этап D — интеграции
После проверки первых этапов можно отдельно рассмотреть GitHub, Allure, импорт результатов и изолированный запуск. Это не входит в первую версию.

## 10. Критерии приёмки первой версии

1. Пользователь может начать генерацию только из принадлежащего ему тест-кейса.
2. Интерфейс и сообщения на русском языке.
3. Поддерживается профиль Java + JUnit 5; неподдерживаемые профили не выдаются за реализованные.
4. Перед каждым потенциально платным запросом требуется явное подтверждение.
5. Используется собственный ключ пользователя; TestRun не оплачивает запросы за клиента.
6. Секретные значения параметров не уходят провайдеру и не попадают в исходный код.
7. Ответ модели проходит строгую валидацию; некорректный ответ не показывается как готовый код.
8. Пользователь видит допущения, вопросы и TODO, может редактировать код.
9. Ничего не сохраняется в тест-кейс автоматически.
10. Экспорт выполняется только по отдельному действию пользователя.
11. TestRun не запускает сгенерированный код и не меняет файлы на сервере.
12. Автоматические тесты подтверждают изоляцию по владельцу, отсутствие утечки секретов, проверку путей и отсутствие выполнения кода.
13. Существующая генерация ручных тест-кейсов продолжает проходить регрессионные тесты.

## 11. Что остаётся за рамками

- обещание, что сгенерированный тест сразу скомпилируется или пройдёт;
- автоматическое определение всех внутренних библиотек проекта без предоставленного контекста;
- выполнение кода на общем сервере;
- автоматические коммиты и pull request;
- автоматическое исправление исходного проекта;
- анализ приватных репозиториев без отдельного подключения и разрешения.
